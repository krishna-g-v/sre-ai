# Natural-Language-to-CLI Execution (AWS CLI / kubectl)

See [[00-overview]], [[03-agent-and-integrations]] (guardrail principle this extends), [[09-ops-runbook-and-proactive-monitoring]] (fixed read-only tool catalog and multi-account AssumeRole access this complements).

This doc covers a second way for domain agents to answer live-ops questions, alongside the hand-written tool functions in [[09-ops-runbook-and-proactive-monitoring]] §3: instead of only calling a pre-built Python function, the agent can generate an actual `aws`/`kubectl` command from the user's question (RAG-assisted, few-shot — the same pattern as text-to-SQL) and execute it directly. This is a genuine architecture extension, not just "add a tool" — the read-only guardrail has to be enforced by a deterministic validator instead of "no mutating function exists in the registry," since `aws` and `kubectl` both expose write verbs in the same vocabulary as the read ones. See §2 for how that boundary is kept.

## 1. Decisions (confirmed with the user, 2026-09-10)

| Topic | Decision |
|---|---|
| Execution mechanism | Shell out to the real `aws` and `kubectl` binaries (installed in the backend image), not an SDK mapping — output looks and reads exactly like what the engineer would see running it by hand. Strict argv parsing (`shlex.split`), `shell=False` always, no shell metacharacters permitted. |
| Relationship to docs/09 §3 fixed tools | Complementary, not a replacement. Hand-written functions (`k8s_get_pods`, `k8s_describe_pod`, `cloudwatch_get_metric`, etc.) stay the primary path for common, well-known questions — fully tested, no generation/validation overhead. The CLI generator is the fallback for anything that doesn't match a known function. |
| AWS service scope | EKS, EC2/VPC, ECR, CloudWatch, and RDS — all metadata/describe-level only. Not S3 object data, not Secrets Manager/SSM/KMS decrypt, not RDS query access or log file contents (§4). |
| Few-shot example corpus | Manually curated to start (~20-30 seed examples), not auto-grown from usage yet. Auto-growth from validated successful executions is an explicit future phase once the validator/retry loop has track record, not built now (§6). |

## 2. Pipeline

```
User question
  → RAG retrieval of similar (question → command) example pairs from the curated corpus (§6)
  → LLM generates a command, few-shot-prompted with those examples
  → Deterministic validator (§3) — hard gate, not a prompt instruction
      - reject anything that isn't `aws` or `kubectl` as the binary
      - reject any verb not on the read-only allowlist for that service (§4)
      - reject any target account/cluster the requesting user hasn't personally registered (§9 — supersedes the group-scoped `integration_scope` model this section originally described)
  → Execute via subprocess: argv list (from shlex, never a shell string), shell=False, timeout, output-size cap
  → On error: feed the error back to the LLM for up to 2 self-correction retries, then give up and say so
  → Second LLM pass turns the raw CLI output into the actual chat answer, same citation-transparency principle as existing tools
```

Credentials underneath all of this stay least-privilege read-only (curated IAM policy + k8s RBAC, per [[09-ops-runbook-and-proactive-monitoring]] §2) as an **independent second layer** — same principle as [[03-agent-and-integrations]] §3: even if the allowlist had a bug, the credentials themselves would reject a write call. Neither layer is trusted alone.

**This only ever executes read commands automatically.** That's consistent with what the fixed tools already do today (`k8s_get_pods` already calls the k8s API immediately, no human approval step) — auto-running a *read* was never the boundary. The boundary is: this pathway must stay architecturally incapable of running a write command. The Ops Runbook/Change-Assistant ([[09-ops-runbook-and-proactive-monitoring]] §4) still only ever renders write commands as text for a human to copy/run — it must never be wired to this executor.

## 3. The validator (hard gate, not a prompt)

Given a generated command string:

1. Parse with `shlex.split` — never pass the raw string to a shell. Reject if parsing fails or if it contains anything indicating a second command (`&&`, `|`, `;`, backticks, `$(...)`) — these shouldn't be reachable via `shlex.split` into a single argv, but the parser output is checked defensively anyway.
2. `argv[0]` must be exactly `aws` or `kubectl` (full path pinned, not resolved from `$PATH`).
3. The subcommand/verb must match the per-service allowlist in §4. Everything not explicitly listed is rejected — allowlist, not blocklist (`apply`, `delete`, `exec`, `patch`, `cp`, `port-forward`, `debug`, `drain`, `cordon`, `uncordon`, `label`, `annotate`, `create`, `run`, `scale`, `rollout restart`/`rollout undo`, any `terminate-*`/`update-*`/`delete-*`/`put-*`/`create-*` AWS operation are all rejected by construction, not by name-checking each one).
4. The target account (and, for kubectl, cluster) must resolve to one the requesting user personally registered under Settings → AWS Accounts (§9) — not a group-wide `integration_scope`, which the fixed tools in [[09-ops-runbook-and-proactive-monitoring]] still use but this pipeline no longer does.
5. Inject safety defaults the LLM didn't think to add: output caps (`kubectl logs --tail=200` if untailed, `aws ... --max-items` if unbounded), explicit `--region`/`--namespace`/`--context` rather than trusting ambient defaults (§5).

## 4. Per-service read-only allowlists

| Service | Allowed verbs (examples) | Explicitly excluded even though "read" |
|---|---|---|
| `aws eks` | `describe-cluster`, `describe-nodegroup`, `describe-addon`, `list-clusters`, `list-nodegroups`, `list-addons` | — |
| `aws ec2` | `describe-vpcs`, `describe-subnets`, `describe-security-groups`, `describe-instances`, `describe-route-tables` | — |
| `aws ecr` | `describe-repositories`, `describe-images`, `list-images` | `get-download-url-for-layer`, `batch-get-image` (image *content*, not metadata) |
| `aws cloudwatch` / `aws logs` | `get-metric-data`, `list-metrics`, `filter-log-events`, `describe-log-groups`, `start-query`/`get-query-results` | — |
| `aws rds` | `describe-db-instances`, `describe-db-clusters`, `describe-db-snapshots` (metadata) | `download-db-log-file-portion` (log *contents*), anything requiring a DB connection (this is describe-level AWS-API access only, never a database query) |
| `kubectl` | `get`, `describe`, `logs`, `top`, `explain`, `api-resources`, `version` | `exec`, `cp`, `port-forward`, `debug`, `delete`, `apply`, `patch`, `edit`, `replace`, `scale`, `rollout restart`/`undo`, `drain`, `cordon`, `label`, `annotate`, `create`, `run`, `attach` |

**Secrets/sensitive-data exclusion is deliberate and load-bearing, not an oversight to revisit.** A generic "run any read command" executor will fetch a real secret value if asked and the credentials allow it — a hand-written tool catalog would never have grown a `get_secret_value` function by accident, so this risk is specific to this capability. Two independent exclusions:
- **IAM policy** (target-account role, per [[09-ops-runbook-and-proactive-monitoring]] §2): no `secretsmanager:GetSecretValue`, no `ssm:GetParameter` with decryption, no `kms:Decrypt`, no `s3:GetObject`, no RDS log-content download.
- **k8s RBAC**: the read-only `ClusterRole` excludes `get`/`list` on the `secrets` resource entirely — not scoped down, not filtered, simply not granted.

## 5. Execution environment — per-request credential isolation

The backend serves multiple users/groups/accounts concurrently from one process. `aws` and `kubectl` both read ambient state from the filesystem (`~/.aws/credentials`, `~/.kube/config`) by default — that's fine for a human's single-user terminal, but unsafe here: two concurrent requests for different groups/accounts must never share or race on the same config file.

- Every invocation builds an **ephemeral, per-request kubeconfig** (temp file, STS-derived exec credentials for that specific assumed role, deleted after the command returns) and passes it explicitly via `--kubeconfig=<path>` — never relies on a shared `~/.kube/config`.
- Every AWS CLI invocation passes credentials via explicit environment variables scoped to that subprocess call (from the cached assumed-role session, built by the same `aws_session.py` AssumeRole helper [[09-ops-runbook-and-proactive-monitoring]] §2 introduced, now fed from the user's own registered account — §9 — rather than a group `integration_scope`) rather than a shared `~/.aws/credentials` file or `AWS_PROFILE`.
- `--region`/`--namespace`/`--context` are always passed explicitly by the validator (§3 step 5), never left to an ambient default that could resolve to the wrong account's cluster under concurrent load.

## 6. Few-shot example corpus

**Implemented differently from the original plan above, documented here as the actual decision.** The original design (previous paragraph, kept for context) was to store examples as tagged KB documents retrieved through the normal RAG path. The actual implementation (`app/services/cli_examples.py`) keeps the same *idea* — semantic retrieval over a curated corpus using the same embedding model as the rest of the system — but as an in-process list embedded in code, not `kb.documents` rows: ~23 seed (question → command) pairs, embedded once and cached (`functools.lru_cache`), ranked against the incoming question by cosine similarity (a plain dot product — vectors are already unit-normalized, and the corpus is far too small to need a real vector index). Reasoning: these examples aren't user content, don't need group-based access control (nothing sensitive in "how do you list EKS nodegroups"), and a Postgres/KB round-trip is a heavier dependency than an in-process lookup table warrants. Manually curated for now (§1) — auto-growth from validated successful executions is still a named future phase, not built. Swapping this module's internals for real `kb.documents` storage later is a contained change (only `get_similar_examples`'s implementation, not its callers in `app/agents/cli_agent.py`).

## 7. Pipeline implementation

`app/agents/cli_agent.py::answer_with_generated_cli` implements the §2 pipeline and is wired into `app/agents/orchestrator.py`'s `live_ops_node` as the fallback when none of the fixed keyword-matched tools apply — the existing fixed-tool fast paths (pod/deployment keywords, log/CloudWatch keywords, alert/Grafana, metric/Prometheus) are untouched; this only runs when none of them match, and only replaces the final answer if the generator actually produces one (falls through to the old default otherwise, so previously-tested behavior is unchanged).

- **Generation**: one LLM call, system-prompted with the few-shot examples (§6) plus a live-built "Known AWS accounts" list (label/account id/region for each account the requesting user has personally registered — §9; not specific resources like cluster/repo/log-group names, which aren't pre-registered anywhere and must be discovered via a read command or resolved from history). Responds with strict JSON: `{"command": "...", "account_label": "...", "cluster_name": "..."}` or `{"cannot_answer": true, "reason": "..."}` — the latter (or any unparseable response) makes `answer_with_generated_cli` return `None`, which is the orchestrator's signal to fall back to its own default rather than surface a confusing partial result.
- **Validate + execute**: dispatches to `run_readonly_aws`/`run_readonly_kubectl` (§3-§5) by sniffing the binary name off the generated command.
- **Retry**: a validator rejection or an `ERROR:`-prefixed execution failure (both deliberate, checkable sentinels — see `cli_executor.py`'s `_run`) is fed back to the LLM verbatim, up to `MAX_RETRIES = 2` additional generation attempts, before falling through to synthesize whatever the last attempt produced (including a still-failing one — the engineer sees why it failed rather than getting nothing).
- **Synthesis**: a second LLM call turns the raw CLI output into the answer, explicitly told to state the exact command that was run (so the engineer can verify/rerun it) and to stay advisory-only.

`app/services/integration_scopes.py` — a small extraction of the `integration_scope` lookup (`scopes_for`) that used to live only in `app/agents/live_ops_agents.py`. As of §9, `cli_executor.py`/`cli_agent.py` no longer use it (they use `app/services/user_aws_accounts.py::accounts_for` instead) — it now exists solely for `live_ops_agents.py`'s fixed tools, which are still group-scoped by design.

**Note (superseded by §9):** the rest of this section and §7a below describe the pipeline as it worked against group-scoped `integration_scope` rows. §9 replaced that access model for this pipeline with per-user registered accounts — the *shape* of everything below (history-awareness, explicit disambiguation over silent fan-out, checkable error sentinels) is unchanged, only *where credentials/target resolution come from* changed. Kept here for the design reasoning, not as the current source-of-truth for how scoping works.

### 7a. Multi-turn, multi-cluster refinement

Found by walking through a realistic conversation ("list all the EKS clusters in the nonprod account" → "list the pods in [that cluster]") rather than by inspection — two gaps this exposed and fixed:

- **History wasn't reaching the generator at all.** `answer_with_generated_cli` originally took only the latest message — "picking the name from above conversation" is structurally impossible without the prior turns. It now takes an optional `history` param (passed through by `orchestrator.py`'s `live_ops_node`) and includes it as real conversation turns in the generation call, same reasoning as every other LLM call in `orchestrator.py` (see that module's docstring).
- **`run_readonly_kubectl` had no notion of "a specific cluster."** Unlike an `aws` command (which names its target inline, e.g. `--cluster-name X`), `kubectl` has no flag for which cluster it talks to — that's a kubeconfig-context concern, resolved server-side. The original implementation just fanned every command out to *every* configured cluster, which is wrong once a group has more than one (asking about one specific cluster would silently also query unrelated ones). Fixed with an explicit `cluster_name` parameter: the generation prompt now requires the LLM to include a top-level `"cluster_name"` field whenever more than one EKS cluster is listed under "Known resources" (resolved from the current question or, via history, an earlier turn) — that value is threaded from the parsed LLM response into `run_readonly_kubectl(..., cluster_name=...)`. With a name given, execution is scoped to just that one cluster; with no name and more than one configured, it asks the user to disambiguate rather than guessing or fanning out; with exactly one cluster configured, no name is ever required.
- **Bonus, same pass**: `run_readonly_aws` was also re-running account/region-level calls (like `eks list-clusters`) once per `integration_scope` row, since the convention is one row per cluster — two clusters in the same nonprod account meant `list-clusters` ran (and printed) twice. Now deduped to one execution per unique `(role_arn, region)` pair before executing.

Covered by `test_run_readonly_kubectl_asks_for_disambiguation_with_multiple_clusters_and_no_name`, `test_run_readonly_kubectl_targets_only_the_named_cluster`, `test_run_readonly_aws_dedupes_scopes_sharing_role_and_region` (`tests/test_cli_executor.py`), and `test_resolves_cluster_from_history_and_passes_it_to_kubectl_executor` (`tests/test_cli_agent.py`), which mirrors the exact two-turn conversation that surfaced this.

## 9. Per-user AWS account registration (Settings page) — replaces group-scoping for this pipeline

**Decision (confirmed with the user, 2026-09-10):** rather than an admin provisioning group-wide `integration_scope` rows (per [[09-ops-runbook-and-proactive-monitoring]] §2) for this feature, every user registers their own AWS accounts under **Settings → AWS Accounts** — self-service, no superuser bottleneck. An engineer with personal admin access to several AWS accounts creates a read-only role in each and adds its ARN to their own list; only they can see or use it, including superusers, who use the exact same screen for their own accounts (no admin view into other users' rows).

This applies **only** to the NL-to-CLI pipeline (`cli_executor.py`, `cli_agent.py`). The fixed tool catalog in [[09-ops-runbook-and-proactive-monitoring]] §3 (`k8s_get_pods`, `cloudwatch_query_logs`, ...) is unchanged and still reads `integration_scope`, admin-provisioned per group — the two access models coexist for two different use cases (this one: interactive, personal, self-service; that one: admin-curated, shared across a group, also what a future background poller per [[09-ops-runbook-and-proactive-monitoring]] §7 would need, since a poller has no "requesting user" to own personal credentials).

**Data model** — `user_aws_accounts` (`app/db/models.py::UserAwsAccount`): `id`, `user_id` (FK, cascade delete), `label` (unique per user — e.g. `"nonprod"`, `"shared-services"`), `account_id` (display only), `role_arn`, `external_id`, `region`, `created_at`. No AWS secret ever stored — `role_arn`/`external_id` are non-secret identifiers for STS AssumeRole (`app/services/aws_session.py`, unchanged); actual credentials are fetched fresh per request from the backend's own base/ambient identity, exactly as before. Every account a user registers still needs its trust policy to trust that *same* backend base identity — the per-account-role-per-user pattern doesn't change who the backend authenticates as, only which role it's allowed to assume.

**API** — `app/api/routes/user_settings.py`, mounted at `/settings/aws-accounts` (module named `user_settings` rather than `settings` deliberately, to avoid shadowing `app.core.config`'s `settings = get_settings()` pattern already used in `main.py`): `GET`/`POST`/`DELETE`, every route scoped to `user.user_id` from the JWT — there is no way to list, add, or delete another user's rows, not even for a superuser. `UserAwsAccountCreate` (`app/schemas/settings.py`) validates `role_arn` looks like `arn:aws:iam::<account>:role/<name>` and rejects a blank label; a duplicate label for the same user returns `409`.

**Executor changes** (`cli_executor.py`): `run_readonly_aws`/`run_readonly_kubectl` now take `user_id` instead of `group_ids`, and source accounts via `app/services/user_aws_accounts.py::accounts_for(db, user_id)`. Resolution to exactly one account replaced the old dedup-and-fan-out logic from §7a: `_resolve_account` picks the account named by `account_label` if given, the single registered account if there's only one, or returns a disambiguation message listing labels if there's more than one and none was specified — same "ask, don't guess" principle §7a established for clusters, now applied one level up at the account. `run_readonly_kubectl` also now always requires `cluster_name` (previously only when >1 cluster was pre-registered) since cluster names are never pre-registered at all anymore, only accounts are — the LLM either already knows the name (from the question or history) or must first generate `aws eks list-clusters` to find out.

**Generation contract change** (`cli_agent.py`): `_describe_known_resources` now lists the user's registered accounts (`accounts_for`), not `integration_scope`-derived resource hints. `GENERATE_SYSTEM_PROMPT` gained an `account_label` field (required whenever more than one account is known) alongside the existing `cluster_name` field (now unconditionally required for any kubectl command, not just when multiple clusters were listed — see previous paragraph for why). `answer_with_generated_cli` takes `user_id` instead of `group_ids`; `app/agents/orchestrator.py`'s `live_ops_node` passes `uuid.UUID(state["user_id"])` (already available in `OrchestratorState`, unlike group scoping which needed no change) at its one call site.

**Frontend** — `frontend/src/pages/SettingsPage.tsx`, reachable via **My AWS Accounts** in the sidebar for every authenticated user (not gated by `is_superuser`): list registered accounts, add one, edit one (`PATCH /settings/aws-accounts/{id}` — label itself isn't editable, delete-and-recreate covers a rename), delete one.

**Tests**: `tests/test_cli_executor.py` and `tests/test_cli_agent.py` were rewritten for the new signatures (account-label disambiguation, unconditional `cluster_name` requirement, no more dedup logic to test since there's nothing left to dedupe once exactly one account is always resolved first); `tests/test_user_aws_accounts.py` covers the `UserAwsAccountCreate` ARN/label validation. No route-level test for `user_settings.py` — it's thin CRUD mirroring the already-established pattern in `app/api/routes/groups.py`, and this repo's unit tests don't stand up a live DB (only `tests/e2e/` does, against a real running stack).

### 9a. Per-account base credentials (2026-09-10) — a deliberate security tradeoff

Once §9 shipped, first real usage surfaced a question worth recording explicitly rather than glossing over: §9 as originally built still required **one shared, centrally-configured base identity** (an access key in the backend's own `.env`, whose ARN every registered role's trust policy must list) — self-service for *which accounts*, but not for *who assumes them*. The user asked to move that too into `user_aws_accounts`, so each user can supply their own base identity instead of coordinating on one shared one.

**This was flagged, not applied silently.** The tradeoff: a role ARN is a non-secret pointer, but an access key is a standing, long-lived credential — storing it means a database compromise (leaked backup, SQLi, an insider with DB access) exposes live AWS credentials, not just role references, with no built-in expiry or rotation. Recommended keeping the shared-base-identity model (the "multiple accounts" concern is already solved by it — the base identity is configured once, ever, not per account). The user considered this and explicitly chose to proceed anyway. Implemented as asked, with harm-reduction built in:

- `UserAwsAccount` gained `access_key_id`/`secret_access_key` (both optional — an account with neither falls back to the shared base identity, so nothing about the original design broke). Documented in the model's own docstring as a conscious exception to "no AWS secret lives in this app," explicitly paralleling `docs/05-auth-and-users.md`'s existing precedent of deferring credential hashing/encryption in v1 — not a new, unprecedented risk class for this codebase, but not zero-cost either.
- **`UserAwsAccountOut` never returns the secret once saved** (`has_own_credentials: bool` instead) — write-only from the API's perspective, same pattern as most credential-management UIs.
- **A real correctness bug this would otherwise have introduced, fixed before it shipped**: `aws_session.py`'s session cache previously keyed only on `(role_arn, external_id, region)`. Once *different base identities* can assume a same-shaped role ARN, that's not unique enough — two different users' credentials (or a user's own credentials vs. the shared ambient identity) could have collided and silently reused each other's cached assumed-role session. Fixed by including the base identity (the access key id, or an `"ambient"` sentinel) in the cache key. Covered by `test_get_aws_session_does_not_share_cache_across_different_base_identities`.
- `PATCH /settings/aws-accounts/{id}` (`UserAwsAccountUpdate`) was added alongside this so an account created before this field existed can have credentials added without deleting and recreating it (which would change its id).

### 9b. Two real gaps found only by attempting a live test

Neither of these showed up in code review or unit tests — both were found by actually trying to exercise the pipeline against the user's real account (`907986008762`, `ap-southeast-2`), which is exactly why that step matters and isn't a formality:

- **The backend image never actually had `aws`/`kubectl` installed.** §1 decided execution should shell out to the real binaries, and `cli_executor.py` was written and unit-tested against that assumption (with `subprocess.run` mocked) — but `backend/Dockerfile` was never updated to install them. `which aws`/`which kubectl` in the running container came back empty. Fixed by installing AWS CLI v2 and kubectl in the final image stage (architecture-detected, amd64/arm64), verified with `aws --version`/`kubectl version --client` in the rebuilt container.
- **No base AWS credentials were configured anywhere.** Storing a role ARN doesn't grant access by itself — `sts:AssumeRole` requires the caller to already be authenticated as some identity the role's trust policy names, and the dev container had none configured at all (`env | grep -i aws` showed nothing). This is what motivated §9a's per-account credential option, but the general point — a role ARN is a pointer, not a credential — applies regardless of which base-identity model is in use.

### 9c. Two more live-testing-only bugs: EKS questions never reached the new pipeline at all (2026-09-11)

Both found by asking a real EKS/kubectl question in chat and getting "no EKS/kubectl integration configured" back — despite a real account being registered and working correctly for EC2/EBS questions. Neither is visible from unit tests, since both are about *routing* (which code path a question reaches), not the pipeline's internal logic, which was already covered.

- **`orchestrator.py`'s `live_ops_node` checked the old, admin-provisioned `integration_scope` keyword-matched tools *before* the per-user CLI pipeline, not after.** The keyword set that triggers the old `k8s_get_pods`/`cloudwatch_query_logs` fast path ("pod", "cluster", "eks", "log", "cloudwatch", ...) unconditionally intercepted every EKS/CloudWatch question first — the new pipeline (docs/10 §9) never got a chance to run for exactly the questions it exists to answer, because almost every such question contains one of those words. Restructured so AWS/EKS-flavored questions try the per-user pipeline first, falling through to the old fixed tools only if the CLI generator itself can't produce an answer — preserving them for whoever *does* configure a group-wide `integration_scope` (e.g. a future background poller, per [[09-ops-runbook-and-proactive-monitoring]] §7, which has no "requesting user" to own personal credentials), while fixing the reported bug.
- **The classifier itself consistently (5/5, not flaky) misrouted a live-ops follow-up to `document_topic`** when the previous turn had listed EKS clusters and the new message said "list the pods in \<cluster name\>" — reproducible with the real LLM, real prompt, no mocking. Root cause: `CLASSIFY_PROMPT`'s bias toward `document_topic` ("classify aggressively toward document_topic", "if unsure, choose this one") wasn't scoped to exclude an obvious live-ops continuation, so it drowned out the vaguer "classify it the same way as that ongoing topic" continuation instruction. Fixed by adding an explicit carve-out: a follow-up continuing a prior turn that itself ran a live investigation stays `live_ops`, even when the follow-up message doesn't repeat keywords like "pod"/"cluster" itself. Verified 5/5 after the fix, plus a regression check against the original document-topic-continuation, bare-greeting, and genuinely-ambiguous cases the prompt was already handling correctly.

Both verified via the actual `build_orchestrator_graph(db).invoke(...)` call the chat endpoint uses — not `answer_with_generated_cli` in isolation — specifically because the bug was in what happens *before* that function is even reached.

### 9d. §9c's own fix was still too narrow: a redundant keyword gate blocked correctly-classified follow-ups (2026-09-11)

Reported directly: "total number of ebs volumes" worked, but the natural follow-up "which is the largest in size of those" fell back to document/RAG-flavored behavior instead of continuing the investigation. The user's own framing was the right diagnosis — once a live-ops investigation is underway, a short follow-up shouldn't need to re-earn its way back into that context on every turn, the same way a document-pinned session doesn't re-derive "is this still about the pinned document" from keyword matching.

Traced it precisely: the classifier already correctly said `live_ops` for this exact case, 5/5, no fix needed there. The actual bug was §9c's own fix — `live_ops_node` gated "try the CLI pipeline" behind a keyword check (`any(k in lowered for k in _AWS_EKS_KEYWORDS)`), and "which is the largest in size of those" contains none of those words. That gate was a leftover from the *old* fixed-tool dispatch (which genuinely needs a keyword to know which tool to call) copied onto the *new* generator (which doesn't — it makes that call itself via `cannot_answer`). Since `live_ops_node` is only ever reached after the classifier has already decided the message is live-ops, a second keyword filter in front of the CLI generator was pure liability with no upside. Removed entirely — the CLI generator is now always tried first for every `live_ops`-classified message, unconditionally, falling through to the old fixed tools only if it returns `None`.

Confirmed live (`answer_with_generated_cli` in isolation) that the generator already resolved "those" back to the 3 EBS volumes from history correctly — the fix was purely about *reaching* it, same shape as §9c's first bug. Full two-turn conversation re-verified through the real graph post-fix: both turns `live_ops`, both real `aws ec2 describe-volumes` calls, correct volume count and correct largest-volume answer.

## 10. Knowledge-base-aware live-ops answers (2026-09-11)

**Decision, from the user directly**: document-session pinning (docs/08) stays exactly as scoped — `document_topic` only, `live_ops_node` never touches `pinned_document_id`, confirmed unchanged. Separately: a live-ops question should also check the knowledge base alongside running commands, not answer from live output in isolation the way it did before this — matching the Ops Runbook idea already scoped in [[09-ops-runbook-and-proactive-monitoring]] §4/§5 (ground a plan in both live discovery *and* uploaded runbook content), now actually wired into the per-user CLI pipeline rather than just documented as a future direction.

**Implementation** (`app/agents/cli_agent.py`):
